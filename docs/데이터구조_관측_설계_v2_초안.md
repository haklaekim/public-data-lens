- 상태: DRAFT (2026-07-29) — 외부 검토안("원본 컬럼 + 예시값" 제안) 분석·수용 결과
- 위상: 설계서 v1.0(동결)의 **확장 계층** — 3층 구조·책임 분리(§2)·식별자 체계(§7)를
  변경하지 않으며, 계약은 부속 명세 semver(minor)로 처리한다. **재개봉 불필요.**

## 1. 목표와 비목표

**목표** — 사용자가 포털에서 파일을 내려받기 전에 답할 수 있게 한다:
"이 데이터에 필요한 컬럼이 실제로 존재하고, 값이 예상한 형식인가?"

**비목표(명시적으로 하지 않음)** — 컬럼 의미 동일성 판정, 실제 조인 가능성 판정,
전체 데이터 품질 평가, 컬럼 정규화·표준 매핑(후속 별도 계층).

**근거 수준 사다리 확장**: `CATALOG_METADATA_ONLY`(현행) → **`FILE_OBSERVATION`**(신규,
파일 구조·예시값 범위) → `API_RESPONSE_SAMPLE`(3차). 신규 수준은 **신규 표면에만** 쓰며
기존 응답의 evidenceLevel은 불변.

## 3. 데이터 모델

```
Dataset (목록키, 불변 URI)                      ← 기존, 불변
 └─ CatalogRecord (목록키-FILE / 목록키-API)     ← 기존, 불변
     └─ StructureObservation (신규, 관측 스토어)  ← 파일/응답 1회 관측 단위
         ├─ FileColumn[]        (1차)
         └─ ApiOperation[]      (3차)
             ├─ RequestParameter[]
             └─ ResponseField[]
```

**관측 스토어는 카탈로그 릴리스와 분리**한다(`data/observations/observations.db` + 파일 보관은
해시 검증 후 폐기 가능). 이유: 월간 목록 스냅샷과 파일 관측은 주기·수명이 다르고,
관측을 릴리스에 넣으면 월간 재현성 모델이 깨진다. 연결 키는 (목록키, list_type)이며
카탈로그 쪽은 관측 존재 여부만 조인해 표시한다.

### StructureObservation
```
observation_id        해시 기반 결정 ID
list_key, list_type   카탈로그 연결 키
structure_status      AVAILABLE | NOT_COLLECTED | SOURCE_UNAVAILABLE | UNSUPPORTED_FORMAT
                      | ACCESS_RESTRICTED | API_STRUCTURE_NOT_SUPPORTED_YET | COLLECTION_FAILED
source_url            실제 접근한 파일 URL/API 엔드포인트
source_sha256         파일 해시(재현성 앵커)
source_format         CSV | XLSX | ...
observed_at           관측 시점(UTC)
tool_version          수집기 버전
rule_versions         적용 판정 규칙들
license_gate          FULL | COLUMNS_ONLY (S0-2 게이트 결과)
row_count_observed    관측 행 수(목록 기재 행 수와 대조용 — 단정 없이 병기)
```

### FileColumn
```
ordinal               원본 순서 (1-base)
source_name           원본 컬럼명 — 절대 변경하지 않음
observed_type         INTEGER|NUMBER|STRING|DATE_LIKE|BOOL_LIKE|EMPTY  (rule: column-type-observation-v1)
examples[]            예시값 ≤10 (license_gate=FULL이고 PII 통과 시에만)
example_method        DISTINCT_UP_TO_10 (결정론: 정렬 후 상위 — 재현 가능)
null_count_in_sample  표본 내 결측 수
pii_status            CLEAR | MASKED | WITHHELD  (rule: pii-screening-v1)
format_note           제한적 관찰("YYYY-MM-DD 형태" 등, rule: format-observation-v1) — 없을 수 있음
```

모든 관측 필드는 **사실 기록**이고, `format_note`만 관찰(해석 아님을 라벨로 명시)이다.

## 4. 판정 규칙 (레지스트리 신규 등록)

| ruleId | 내용 |
|---|---|
| `column-type-observation-v1.0` | 표본 기반 유형 관측 — 전량 정수면 INTEGER 등. 표본 한정임을 정의에 명시 |
| `example-extraction-v1.0` | 결정론적 발췌: 전량 스캔→DISTINCT→정규화 정렬→상위 10. 첫 10행 방식 금지 |
| `pii-screening-v1.0` | 컬럼명 사전(성명·전화·이메일·상세주소·차량·계좌·식별번호…) + 값 패턴(전화·이메일·주민번호 정규식) 이중 탐지. 걸리면 WITHHELD(기본) 또는 MASKED. **미탐지 보완: 신고 시 24h 내 제거 절차** |
| `structure-status-v1.0` | 상태값 의미와 전이 규칙 |

응답의 모든 관측에는 해당 rule 버전이 동반된다(§5 원칙 승계).

## 5. 수집 파이프라인 (신규 `pipeline/observe/`)

```
후보 선정 → 다운로드 → 파싱 → 관측 추출 → PII 스크리닝 → 라이선스 게이트 → 저장
   │            │         │                                            └ 실패도 상태로 기록
   │            │         └ 인코딩 추정(cp949/utf-8), CSV/XLSX 한정(1차)
   │            └ 예절: 동시 1~2, 요청 간격, 야간 배치, 표준 UA, 재시도 상한
   └ 우선순위 정책(아래)
```

**커버리지 정책(실측 기반)** — 전수(83,695)가 아니라 단계적:

| 웨이브 | 대상 | 규모 |
|---|---|---|
| W1 | 표준데이터(STD 연계 300종) + 국가중점 FILE | ~4,000 |
| W2 | 다운로드 1,000+ FILE | ~20,000 |
| W3 | §12 사용 로그의 수요 신호(검색·조회된 recordId) 기반 온디맨드 | 지속 |

화면·Tool은 커버리지를 항상 노출한다("구조 확인 20,067/83,695건"). `NOT_COLLECTED`는
품질 문제가 아니라 수집 순번임을 문구로 구분한다.

**재수집**: 월간 목록에서 `modified_date`가 바뀐 관측 대상만 재방문. 파일 해시 동일 시
관측 재사용(observed_at만 갱신). 스키마 변경(컬럼 증감·개명)은 관측 diff로 기록 — 2차의
"스키마 변경 이력" 원천.

## 6. 개인정보·라이선스 통제 (기능보다 먼저)

1. 예시값 기본 정책: **컬럼 단위 발췌만**(행 단위 금지 — 재식별 결합 차단)
2. PII 이중 스크리닝(§4) — 기본값은 보수적으로 WITHHELD
3. 라이선스 게이트: `NO_RESTRICTION`만 예시값, `OTHER`(16.4%)는 컬럼명·유형만
4. **예시값은 검색 인덱스에 넣지 않는다** — 컬럼명만 FTS 대상(2차)
5. 데이터셋 단위 제외 목록(기관·개인 요청 시) + 신고 → 제거 절차를 고지문에 추가(§10 개정)
6. 컨시어지·LLM에 예시값 전달 시에도 동일 게이트 통과분만
7. README의 "실데이터 재배포 없음" 문구를 "라이선스가 허용하는 범위의 컬럼별 예시값
   발췌 제공"으로 갱신(공개 문구 정합)

## 7. 표면 설계

### MCP — `get_dataset_structure` (부속 명세 v1.2, minor 추가)

```jsonc
// 입력: recordId, includeExamples(기본 true), maxExamples(≤10)
// 출력(FILE, AVAILABLE):
{
  "data": {
    "recordId": "15012345",
    "distributionType": "FILE",
    "structureStatus": "AVAILABLE",
    "evidenceLevel": "FILE_OBSERVATION",
    "coverageNote": "원본 파일 1개의 관측 — 전체 배포본·전체 값을 대표하지 않음",
    "source": { "format": "CSV", "sha256": "…", "observedAt": "…", "url": "…" },
    "columns": [ { "ordinal": 1, "sourceName": "시설명", "observedType": "STRING",
                   "examples": ["중앙경로당", "행복경로당"],
                   "exampleMethod": "DISTINCT_UP_TO_10", "nullCountInSample": 0,
                   "piiStatus": "CLEAR", "rule": "column-type-observation-v1.0" } ],
    "rowCountObserved": 1520,
    "rowCountListed": 1518   // 목록 기재값 병기 — 대조는 사용자/호스트 몫
  },
  "meta": { "...": "공통 봉투 — ruleVersions에 관측 규칙 포함" },
  "warnings": ["예시값은 관측 표본이며 전체 분포·품질을 대표하지 않습니다. ..."]

// 미수집: structureStatus=NOT_COLLECTED + 사유 + 포털 링크 (오류가 아닌 정상 응답)

```

기존 Tool·카드 뷰는 **불변**. 검색 요약에는 `structureAvailable: true` 한 필드만 추가(minor).

### REST/웹
- `GET /api/datasets/{id}/structure` — 동일 봉투
- 프로필에 **"데이터 구조" 탭**: 순서·원본 컬럼명·관측 유형·예시값·표본 관찰 표 +
  관측 출처(파일·해시·시점) + 커버리지·면책 문구. 검색 카드에 `구조 확인됨` 칩
  (기존 keyFields 칩 열에 자연 편입)

### 정본 URI (§7 확장)
`/projects/datanav/record/{recordId}/structure` — 관측 JSON-LD(kdp:StructureObservation,
PROV로 파일 해시·시점·도구 귀속). 1차엔 Tool/REST만, 안정화 후 정본화.

| 단계 | 범위 | 수용 기준(§11 스타일) |

S1의 규모감: 수집기·스토어·규칙 4종·Tool·웹 탭 — 기존 파이프라인 패턴 재사용 시
집중 작업 수일 규모(수집 웨이브 실행 시간은 별도, 포털 예절 속도에 종속).

## 9. AIRD 연계 (연구 트랙 — 검토안 미포함 보완)

파일 관측은 AIRD 실증의 다음 장을 연다: 관측 스토어의 유형·결측·유일성 신호는
개별 데이터셋 MMI 지표(D6-01 유일성, D7-02 기술적 유효성 등)의 **실측 원천**이 된다.
단, v2에서는 지표를 산출하지 않는다 — 관측만 축적하고, 개별 AIRD 진단·DM 부여는
표본·규칙이 검증된 후의 별도 결정으로 남긴다(성급한 등급 부여 금지 원칙 유지).
