# Planning Agent 설계 v1 (초안) — 검색 결과에서 데이터 활용계획으로

- 상태: **초안 — 검토 대기** (2026-07-31)
- 전제 문서: 설계서 v1.0 확정판(§2 책임 분리·§10 로그·§11 수용 기준),
  데이터구조 관측 설계 v2.2, 외부 기능 검토(2026-07-31, 전략 방향 채택),
  컨시어지 v0.5 미니 벤치마크(golden/bench_v0_report.json)
- 포지셔닝(채택): **공공데이터 렌즈는 발견에서 그치지 않고 실제 사용 가능성을 검증하여
  선택 근거·결합 방법·실행 순서와 한계를 판단하도록 지원하는 공공데이터 신뢰 인프라다.**
- 관계: 현행 컨시어지(프롬프트 v1.2, 계약 v1.3.0 Tool 소비)는 **Planning Agent v0**다.
  본 설계는 v0를 폐기하지 않고 상태 전이·검증 축·산출 스키마를 명시화해 v1으로 승격한다.

## 0. 실증 근거 — 왜 이 방향인가

v0.5 미니 벤치마크(25문항×2조건, 결정적 채점)가 설계의 출발점이다:

| 지표 | 카탈로그만 | 구조 관측 포함 |
|---|---|---|
| 관련성 P@3 | 0.560 | 0.653 |
| 구조 인용률(관측 스토어 대조) | 0.373(추측이 우연히 일치) | 0.613(관측 인용) |
| 근거 없는 참조(grounding 제거) | 8건 | **0건** |

→ **검증 가능한 관측 근거가 계획의 정확성을 직접 끌어올린다.** v1의 모든 설계 결정은
"판단을 호스트 LLM의 그럴듯함이 아니라 서버의 관측 사실에 묶는다"로 수렴한다(§2 정합).

## 1. 위치와 책임 분리

```
사용자 목적 ─→ AI 컨시어지(B 서비스, 사용자 경험)
                └─ Planning Agent(내부 엔진, 본 설계)
                     ├─ 상태 전이·재탐색 결정 ..................... LLM(해석)
                     ├─ Evidence Evaluator(적합성 판정) ┐
                     └─ 공개 MCP Tool 8종(사실 계층) ────┴─ 서버(결정적·재현 가능)
```

- **서버가 판정하는 것**(재현 가능): 컬럼 실존, 커버리지 상태, 라이선스 게이트, 완전성·
  신선도, 컬럼 교집합, 근거 수준. → Evidence Evaluator는 새 판단 로직이 아니라
  **기존 Service 판정의 묶음 호출**이다(판단 이중화 금지).
- **호스트(LLM)가 해석하는 것**: 목적 분해, 요건 도출, 축별 사실의 목적 적합 종합,
  대안 탐색 방향. 단, 모든 주장에는 근거(recordId·관측 컬럼·판정 코드)를 붙인다.
- 공개 MCP는 v1에서 변경 없음 — Planning Agent는 계약 v1.3.0의 소비자다.

## 2. 상태 전이 명세 (제한형 플래너)

v0의 암묵 절차(검색→구조 확인→JSON)를 명시적 상태로 승격한다. 무제한 자율 탐색은
비용·무근거 계획을 늘리므로 채택하지 않는다(외부 검토와 합의).

```
GOAL ─→ REQUIREMENTS ─→ SEARCH ─→ VERIFY ─┬→ JOIN_PLAN ─→ PLAN
  │(불명확)                     ↑          │(미충족 요건 존재·재탐색<K)
  └→ CLARIFY(즉시 종료·되물음)   └──────────┘ RESEARCH
```

| 상태 | 하는 일 | 산출(서버 보관) | 전이 조건 |
|---|---|---|---|
| GOAL | 목적 구조화(대상·의사결정 단위·공간/시간 차원) | goal 객체 | 불명확→CLARIFY, 명확→REQUIREMENTS |
| CLARIFY | 명료화 질문만 하고 종료(추측 생성 금지 — v0 실증 동작 유지) | 질문 목록 | 사용자 재입력 대기 |
| REQUIREMENTS | 요건 원장 생성 — 역할 4종(핵심/보완/기준/검증)별 필요 데이터 정의 | requirements[] (status=미충족) | 항상 SEARCH |
| SEARCH | MCP 검색(키워드+컬럼+필터 병렬) | 후보 풀(seen_ids) | 항상 VERIFY |
| VERIFY | 후보×요건을 8축 판정(§3) — 서버 사실 우선 | 후보별 verdict, 요건 status 갱신 | 미충족 요건 있고 재탐색<K → RESEARCH, 아니면 JOIN_PLAN |
| RESEARCH | 미충족 요건만 겨냥한 재검색(검색어 변형·컬럼 검색·대안 탐색) | 후보 풀 확장 | VERIFY로 복귀(재탐색 횟수 +1) |
| JOIN_PLAN | 채택 후보 간 결합 계획 — 관측 컬럼 근거의 조인 키만 '확인'으로 표기 | joinPlan[] | 항상 PLAN |
| PLAN | 활용계획 JSON(plan-v1) 생성·검증·grounding 게이트 | plan-v1 문서 | 종료 |

**상한(운영 통제)**: 재탐색 K=2(총 탐색 3회), Tool 왕복 ≤6턴, Tool 호출 ≤20회,
캡 4겹은 v0.5 그대로 적용. 상한 도달 시 미충족 요건을 unverified/limitations로 정직하게
남기고 PLAN으로 진행한다(실패가 아니라 "한계가 명시된 계획").

**구현 방식(권고)**: 상태별 분리 LLM 호출이 아니라 **단일 대화 + 서버 오케스트레이션
하이브리드** — 서버가 요건 원장·재탐색 카운터·상태를 보관하고, 각 상태의 산출을 구조화
출력(스키마 강제)으로 받아 다음 상태 프롬프트에 주입한다. v0 대비 비용 증가를 왕복 +2턴
이내로 억제하면서 상태·원장을 감사 가능하게 만든다.

## 3. 적합성 검증 8축 판정표 (Evidence Evaluator)

| 축 | 판정 질문 | 판정 주체·근거 | v1 가용성 |
|---|---|---|---|
| 내용 | 목적과 대상이 일치하는가 | 호스트(제목·설명·키워드 해석) | 현재 |
| 구조 | 필요 컬럼이 실존하는가 | **서버** get_dataset_structure(관측 컬럼) | 현재(FILE 71%) |
| 공간 | 분석 단위(전국/시도/시군구)가 맞는가 | 서버 keyFields.spatial·regions(근거 수준 동반) + 호스트(범위값 해석) | 부분 |
| 시간 | 기준 시점·갱신이 적절한가 | 서버 keyFields.temporal·freshness(목록 수준 명시) + 호스트 | 부분 |
| 접근성 | 파일/API를 실제로 받을 수 있는가 | 서버(향후 접근 관측) | **후속 — S0-3 약관 관문**(§7) |
| 결합 | 식별자·코드·좌표로 연결 가능한가 | 서버 structureComparison(교집합)+관측 컬럼, 호스트(의미 동일성은 비단정) | 초급(현재)→컬럼 레지스트리 연계(후속) |
| 이용 | 라이선스·제공 조건 문제 없는가 | **서버** 라이선스 코드·게이트 | 현재 |
| 근거 수준 | 메타 추정인가 실관측인가 | **서버** evidenceLevel·coverageStatus | 현재 |

- 축별 판정값: `PASS / CONDITIONAL / FAIL / UNKNOWN(미수집·미관측)`. UNKNOWN은 FAIL이
  아니다 — "결과에 없음 ≠ 없음" 원칙을 축 판정에도 적용한다.
- 종합 verdict: `적합 / 조건부 적합(조건 명시) / 부적합(사유 축 명시) / 판단 불가`.
  **LLM이 점수를 창작하지 않는다** — 축 판정값의 조합 규칙(서버 코드)으로 도출한다.

## 4. 부적합 판정·대안 제시 규칙 (차별점의 명문화)

v0.5 실증 패턴("주소 기반, 좌표 미포함 → 지오코딩 또는 대체 후보")을 규칙으로 고정한다:

1. FAIL/CONDITIONAL 판정에는 **사유 축과 관측 근거**를 반드시 병기한다
   (예: 구조 FAIL — "관측 컬럼 34종에 위도·경도 없음, 소재지도로명주소 있음").
2. FAIL 후보를 버리지 않고 계획에 **excluded[]로 남긴다** — "추천하지 않는 이유"가
   추천만큼의 정보 가치를 갖는다(외부 검토 §와우 포인트 수용).
3. FAIL 사유가 해소 가능하면 **대안 경로를 최소 1개** 제시한다: ①변환(지오코딩·코드 매핑)
   ②대체 데이터(재탐색으로 실존 확인된 것만) ③범위 축소. 해소 불가면 한계로 명시한다.
4. 대안도 같은 8축 검증을 통과해야 candidates에 승격된다 — 검증 없는 대안은
   complementaryData(제안)에만 둔다.

## 5. 활용계획 산출 스키마 plan-v1 (v0 대비 additive)

v0 스키마(answer·purposeBreakdown·candidates·insights·pipeline·complementaryData·
expectedJoinKeys·followUps·unverified·limitations)는 유지하고 다음을 추가한다:

```jsonc
{
  // --- v1 신설 ---
  "goal": {"objective": "...", "decisionUnit": "시군구|격자|...", "spatial": true, "temporal": true},
  "requirements": [
    {"id": "R1", "role": "core|complement|reference|validation", "need": "...",
     "status": "MET|PARTIAL|UNMET", "coveredBy": ["recordId"]}
  ],
  "candidates": [ /* v0 필드 + */ 
    {"verdict": {"fit": "적합|조건부|부적합|판단불가",
                 "axes": {"structure": "PASS|...", "license": "...", "...": "..."},
                 "evidence": ["위도·경도 컬럼 관측(2026-07-29)", "..."]}}
  ],
  "excluded": [{"recordId": "...", "reason": "구조 FAIL — ...", "alternative": "..."}],
  "joinPlan": [
    {"left": "recordId", "right": "recordId", "key": "행정구역코드",
     "keyEvidence": "OBSERVED|INFERRED",   // OBSERVED = 양쪽 관측 컬럼 실존
     "transform": "주소→법정동코드 변환 필요", "confidence": "high|medium|low"}
  ],
  "collectionOrder": [{"step": 1, "recordId": "...", "note": "..."}],
  "searchLedger": {"rounds": 2, "toolCalls": 14, "unresolved": ["R3"]}  // 감사 가능성
}
```

- 계약 지위: plan-v1은 **컨시어지(B) 응답 계약**이다 — 공개 MCP 계약(v1.3.0)과 별개로
  버전을 관리한다(concierge-plan-v1.0). grounding 게이트는 신설 필드의 recordId에도
  동일 적용한다(joinPlan·excluded·requirements.coveredBy 전부).

## 6. 사용 결과 자산 — §10 정합 설계 (수집 시작 전 필수)

축적 대상(외부 검토 §6-4)과 프라이버시 통제를 함께 정의한다. **고지문 개정(D1) 전에는
수집을 시작하지 않는다.**

| 이벤트 | 수집 필드 | 명시적 비수집 |
|---|---|---|
| plan_issued | plan-v1 요약(요건 수·verdict 분포·검색 라운드), anon(HMAC) | 질문 원문은 기존 §12 정책 그대로 |
| candidate_excluded | recordId·사유 축 코드 | 자유 서술 |
| plan_adopted | 사용자가 명시적으로 "채택" 액션 시에만: recordId 목록 | 암묵 추정(체류 시간 등) 금지 |
| feedback_broken | 사용자가 신고한 recordId·유형 코드 | 연락처(계정 자체가 없음) |

- 옵트아웃(DNT/GPC/X-Datanav-No-Log) 시 **전면 미기록** — 기존 원칙 그대로.
- 익명 식별자는 영속 HMAC 키 기반(v0.5 구현) — 원 IP 미저장·역산 불가 유지.
- 보존 12개월, api 자체 삭제(월간 빌드와 분리 — v0.5 구현 재사용).
- 활용: 집계 통계(요건 충족률·부적합 사유 분포·재탐색 효율)로만 공개하고,
  개별 이벤트는 서비스 개선 내부 용도로 한정한다.

## 7. 공개/비공개 경계 (외부 검토 §6 수용)

- **공개(무료·개방)**: MCP 사실 계층 전부, plan-v1 스키마 문서, 벤치마크 하니스·결과.
- **B 서비스(비공개 로직)**: 요건 도출 프롬프트, 축 조합 규칙의 세부 가중, 재탐색 전략,
  업무별 계획 템플릿, 사용 결과 자산.
- 원칙: **MCP는 사실과 근거를 개방하고, 컨시어지는 그 근거로 판단과 계획을 제공한다.**

## 9. 수용 기준 (§11 스타일 — 벤치 게이트)

25문항 기준(골든셋 v1 승격 후 확대). v0.5 실측을 하한으로:

1. 관련성 P@3 ≥ 0.65 (v0.5=0.653 유지 이상)
2. 구조 인용률 ≥ 0.60, **관측 대조 불일치 주장 0건**
3. grounding 제거 0건 유지 (joinPlan·excluded 포함 확대 적용에서도)
4. 요건 원장 정합: UNMET 요건이 unverified/limitations에 100% 반영
5. 명료화 정확성: 불명확 질문 셋(신설 10문항)에서 되물음 ≥ 80%, 명확 질문에서 오되물음 ≤ 8%
6. plan-v1 스키마 검증 통과율 100%, 왕복 ≤6턴·비용 문항당 상한 내
7. 테스트 기준선 회귀 없음(112+신규)

## 10. 결정 필요 사항 (사용자)

- **D1. 고지문 개정** — §6 사용 결과 자산 수집 항목의 고지 반영(개인정보_로그_고지 v1.1).
  승인 전 수집 금지.
- **D2. 재탐색 상한 K** — 권고 2(총 3회). 비용과 충족률의 균형점은 벤치로 재검증.
- **D3. verdict 축 조합 규칙의 공개 수준** — 규칙 자체를 공개 문서화할지(신뢰성↑),
  비공개 로직으로 둘지(모방 방어). 권고: 축 판정값 정의는 공개, 조합 가중은 비공개.
- **D4. 골든셋 v1 승격** — 검수 3문항(G09·G37·G39) 포함 인간 검수 후 relevantRecordIds
  고정. 벤치 게이트의 신뢰 전제.
- **D5. 접근성 축 착수 관문** — 포털 약관의 자동수집 조항 확인(S0-3, 기존 기록과 동일).
